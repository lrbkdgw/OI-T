# OI-T

一款以中学 OI 校队为主题的 **3D 像素风经营与养成游戏**。你是一名教练，要在有限的课时、机位、经费和个人精力之间安排训练，陪学生走过入队、比赛、转折与毕业，让一间旧机房逐渐拥有自己的传统。

**当前状态：设计阶段。** 本仓库收录策划方案、内容原型与开发规格，尚无可运行游戏、构建脚本或已确定的引擎。文档里的价格、概率、成长速度、合同和地区规则均为待验证的游戏草案。

## 这是一场怎样的经营

你管理的不只是成绩。一名学生已经想出解法，却总在截止前写不完；另一名学生数学很好，但对陌生评测环境紧张；初三的骨干希望先准备中考；新来的学弟还缺最基础的前置知识。把所有人塞进同一张高难题单，可能短期省事，却会让下一次比赛和下一届交接暴露问题。

钱同样需要取舍。两台主机是否能增加机位，取决于空槽是否已有配套；承办补贴是否盈利，要看服务器、备用机、筹备工时与尾款何时到账；一位兼职助教能分担课程，却也需要薪资、排班和交接。

游戏没有强制通关终点。学校可能缩编、整改、失去资质，学生也会离开，但始终保留重新经营的基础条件。已经发生的训练、故事和合法荣誉组成校史，下一届不必复制上一届的成功方式。

## 核心体验

- **学生有不同的成长路径**：知识、实现、调试、策略、目标与家庭共同影响选择，隐藏天赋通过真实表现逐步揭示。
- **规则能解释结果**：部分分、提交版本、测试组、时间预算、环境与检查习惯共同形成成绩，赛后能追到失分原因。
- **建设改变工作方式**：场地、网络、供电、维修和施工决定哪些活动能同时进行，房间主题与纪念物负责表达历史。
- **关系依赖兑现**：承诺休整要真的改课，承诺讲评要真的排人；关系不能替代资格、经费与证据。
- **长期经营有新问题**：世代断档、教师流动、地区对手、政策过渡、品牌赛事和学长回访改变多年局势。
- **重复操作可以委派**：周计划、机位轮换与有限自动调整减少排课负担，重要选择仍交还教练。

## 核心循环

~~~text
招生与观察 → 分组与目标 → 课程 / 练习 / 休息 → 模拟赛 → 复盘与调整
     ↑                                                      ↓
新生与学长 ← 校史与交接 ← 设备 / 经费 / 声誉 / 合规机会 ← 正式赛事
                                ↓
                    扩建、团队、合作、承办与地区生态
~~~

短期决定一个时段怎么用，中期检查学生状态与预算，长期面对赛季成绩、毕业交接与学校兴衰。小游戏式细节服务于这些决策，不要求玩家亲自为每名学生写代码。

## 一周里真正会发生的选择

| 处境 | 可以做什么 | 实际代价与后果 |
|---|---|---|
| 十人只有八台健康电脑 | 分组错峰、纸笔课与自主练习、修复或采购 | 错峰不用立刻花钱，但每人上机时间与教学形式不同 |
| 连续两场会做却没交卷 | 限时实现、保底策略、提交检查或暂缓参赛 | 占用原有训练时段，不直接送编码属性 |
| 家长担心学业 | 共同约定文化课、训练上限与复查日期 | 竞赛进度可能放慢，承诺要按出勤核验 |
| 成绩够线但名额有限 | 依公开办法选拔、申请允许的观察机会 | 资格与席位分别检查，不能凭关系复制名额 |
| 想承办三十人比赛 | 准备至少三十三台有效电脑和对应人员 | 还需要资质、备用电源、工期与现金，不是一笔补贴按钮 |
| 高年级即将毕业 | 交接知识、资料、师徒与项目 | 指导者让出个人训练，保留下一届培养能力 |
| 学生不想继续冲奖 | 改为兴趣路线、有限参赛、暂停或体面退役 | 目标可以改变，档案和已获得成绩保留 |

具体可玩的事件与人物线见[事件库](docs/16-event-library.md)和[人物故事](docs/12-relationships-and-student-stories.md)。

## 培养、经营和世界如何继续展开

### 培养不是单纯刷高难题

课程按前置与目标展开，既有普及、提高、专项、综合路线，也有反例收集、实现拆分、代码审阅和小型解题研究。教练可以给不同组开不同课，安排十二周计划，再根据诊断赛调整。题目是否已见过、题库是否验收、解法是否真正独立，都影响这次训练能说明什么。

36 个课程节点、四条路线和教研流程见[课程与题库](docs/10-curriculum-and-research.md)。36 项天赋候选、八种成长曲线与能力周训练见[个人成长](docs/23-talents-and-personal-growth.md)。这些数量是内容设计库规模，不代表每名学生都持有全部能力标签。

### 教练也要经营一个工作团队

主教练、助教、技术支持、文化课协作和辅导支持有不同职责。招聘包含试岗和供给条件，合同限定可服务时段，优秀教师也不能同时监考、讲课又修服务器。学校领导会关注目标、经费与稳定性，年度评议需要过程证据。

教师培训、职称、代课、离职与家校共识见[团队与制度](docs/11-team-staff-and-institutions.md)。

### 机房之外还有校园与地区

扩建不是瞬间增加容量：要腾挪旧设备、隔离施工、预留临时场地、铺设线路、采购配套并验收。宿舍、餐饮和交通服务于已有活动；天气和距离影响行程，而非随机扣分。

地区采用六种虚构生态原型，分别改变交通、经费、学校密度与合作供给。对手有训练风格和真实年级结构，联盟能共享公开资源，但不能共享未公开赛题或绕过名额规则。详见[校园后勤](docs/13-campus-construction-and-logistics.md)与[地区竞争](docs/14-regions-and-season-ecology.md)。

### 成绩之外可以建立学校品牌

公开课、短期培训、设备赞助、题库服务、公益活动和校友基金提供不同合作方式。合同明确现金与实物、备课与授课、阶段交付与取消责任；学校不靠重复签同一协议无限刷钱。

九类合作范本见[赞助与品牌](docs/15-sponsors-outreach-and-school-brand.md)。既要看项目最终盈余，也要看执行期间是否会缺钱或没人上课。

### 多年之后留下什么

一次普通告别、没有证明出来的猜想、第一份可靠检查单和一张旧照片，都可以成为校史。48 项成就关注教学、比赛、经营、承办、传承与探索；装饰和徽章不提供隐藏战力。

年鉴、照片、校服、荣誉室和快照回顾见[玩家表达](docs/18-achievements-and-player-expression.md)。标准开局之外还可选择八种特色场景和自愿挑战，见[剧本与难度](docs/17-scenarios-and-difficulty.md)。挑战结束或退出后仍可继续经营。

- **想看游戏是否有趣**：本页 → 人物故事 → 事件库 → 特色开局 → 玩家表达。
- **想制作日常玩法**：时间训练 → 课程教研 → 教师团队 → 长期计划 → 一周数值对照。

## 统一口径

| 项目 | 约定 |
|---|---|
| 正式标准新档 | 现金30,000，已含当期秋季拨款；6名学生，12机位槽，8台旧电脑 |
| 特色场景 | 可以覆盖开局参数，场景页必须写清现金、设备、人数与附带义务 |
| 原型测试名单 | 10名固定学生，固定机房；与正式标准开局区分 |
| 标准日历 | 每月30日、每学年360日，每天上午/下午/晚自习/夜间四时段 |
| 现实速度 | 标准模式1×每游戏日约10分钟，10×约1分钟；暂停和交互另计 |
| 精简模式 | 每年120可操作日，每日覆盖3个连续标准日，不能跳过中途结算 |
| 数值尺度 | 属性与能力0～100，知识等级0～10，概率0～1，货币为整数游戏单位 |
| 训练规则 | 普通知识成长可解释、非随机；不同知识标签分配同一总XP |
| 比赛结果 | 相同规则、存档与操作可复现；倍速、镜头、面板不改变结果 |
| 信息边界 | 无反馈赛只显示自测和主观进展，真实成绩等规则允许后公开 |
| 经费基线 | 六人无收费外聘的基础运营1,500/月；新增套餐与合同另计 |
| 软失败 | 保留至少三人基础教学条件、教练、校史与继续经营的机会 |
| 表达内容 | 纯装饰、照片、徽章不提供隐藏成长或参赛加成 |

赛事、升学、地区和承办奖励采用版本化游戏规则包。文档不承诺现实某年度的保送、强基、加分或东道主席位政策；如未来制作现实规则包，另标来源与适用年份。

## 设计的采用方式

01 是体验总览，02～09 定义基础契约，10～23 是进一步展开的系统与内容候选。扩展写清接入阶段，不因为文档已经写出就自动进入 MVP。

参数有明确归属：训练系数看02，学生状态看03，比赛评分看04，基础经费和名额看05，永久能力与天赋的进一步细则看23。专题里的算例、特色开局和可选合同只在注明前提下成立，不能把它们拼成一份无额外成本的标准开局。

更新规则时同步相关数值与故事，尤其检查：一个时段是否占用两次、一次费用是否重复计算、同一事件是否重复创建、一个席位是否被复制、隐藏成绩是否从动画或通知泄露。具体可观测行为优先于模糊的“成长更快”“更有氛围”。

## 第一份可验证的交付

先完成固定机房原型：为10名测试学生编辑一周日程，比较讲课与休息，进行一场有部分分的简化模拟赛，安排讲评，保存并读取同样的进度。

课程库、完整招新、自由建设、教师合同、地区竞争、承办、人物长链、自动托管与年鉴都按后续阶段加入。原型通过条件见[开发阶段与验收](docs/09-development-plan.md)，不以一次实现整套百科式设计为前提。
