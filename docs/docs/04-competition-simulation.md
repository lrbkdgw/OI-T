# 比赛与评测模拟

[返回 README](../README.md) · [时间与训练](02-time-and-training.md) · [承办与名额](05-economy-and-hosting.md)

比赛模拟需要回答三件事：学生为什么选择这道题、为什么拿到这些分、玩家能在复盘后改变什么。初版通过结构化解题过程生成结果，不实际运行学生生成的 C++ 代码。

## 1. 一场比赛的数据

一份赛事配置至少包含：

- 稳定 ID、届次、规则版本、报名与比赛时间、参赛资格、席位来源。
- 比赛天数、每天题目列表、虚拟分钟预算、占用的经营时段。
- 反馈模式、提交次数限制、单题提交选择策略、封榜时间。
- 语言与编译环境、文件 IO、时间与空间限制、允许操作。
- 子任务、测试点组、依赖关系、分值和可选择的解法。
- 排名范围、同分处理、奖项与晋级规则、复核窗口。

正式赛在开赛时固化规则快照。普通政策更新不改变进行中的赛事；只有明确的紧急更正可以产生新评测版本。

## 2. 比赛流程与时间预算

~~~text
报名校验 → 锁定参赛名单与规则 → 分配日程 → 开赛
  → 阅读 → 选题 → 构思 → 编码 → 自测 → 提交或改写
  → 截止锁卷 → 统一评测 → 临时成绩 → 复核 → 正式成绩与奖励
~~~

经营层以时段推进，比赛内部默认用 5 个虚拟分钟为一个决策步；这些子步骤消耗同一场比赛的固定预算，不额外推进一个游戏日。

- 每天的预算分别计算。两天赛不能把第一天剩余时间转到第二天。
- 每个决策步只更新当前任务，不在每帧重新抽“能否做出”。
- 学生的构思、编码、自测和改写都消耗时间；截止时未提交的草稿不产生得分。
- 选题策略按可见难度、预计耗时、部分分收益和已耗时间估计，不读取真实隐藏分数。
- 应试策略较高的学生更容易及时止损，保留检查时间；默认可配置最后 15 分钟检查文件、编译和边界。
- 训练赛可提前设置“稳拿部分分 / 均衡 / 冲满分”策略。正式赛开始后不能由教练直接替学生改题序。

## 3. 能力与成功概率

### 3.1 统一尺度

知识点等级为 0～10，参与比赛计算时先乘 10。思维、编码、细节、心理、应试策略、调试、骗分、卡常等属性均采用 0～100。

~~~text
K = Σ(相关知识点等级 × 10 × 权重)，权重之和 = 1
A = 0.6K + 0.25思维 + 0.15应试策略
状态修正 B = clamp((体力-50)/10 + (心情-50)/20 - 压力/20 + RP修正, -12, 12)
RP修正 = clamp((RP-50)/50, -1, 1)
P(构思成功) = sigmoid((A - 解法需求D + B) / σ)
sigmoid(x) = 1 / (1 + exp(-x))，σ 默认 12
~~~

每个学生、题目、候选解法在首次投入构思时生成一个稳定的成功阈值。达到所需构思时间后比较一次；继续投入时间只在解法允许的明确重试节点生效，不能每个子步骤重新掷骰直到成功。

天赋可调整对应能力、耗时或波动，但同一效果只进入一个环节。例如“手速怪”缩短编码时间，不同时额外增加解题概率和评测分数。

### 3.2 时间与挂分

~~~text
编码耗时 = 基础码量分钟 × 100/(50+编码) × 环境不熟悉系数
自测耗时 = 解法基础检查分钟 × 100/(50+调试能力)
p_bug = clamp(基础挂分率 × (1-细节/150) × (1+疲劳/100)
              × (1+压力/200) × 天赋系数, 0, 0.6)
~~~

每个提交版本只生成一次错误集合，包含错误类型、影响的测试点组、是否已被自测发现。检查可以按调试能力发现并修复实际存在的错误，消耗剩余时间；不能反复检定“凭空生 Bug”。

思路失败与实现挂分分别记录。低分既可能是不会，也可能是会做但没写完；报告不能把所有失分都解释成细节差。

## 4. 子任务与解法

子任务是独立的计分单元，分值总和等于题目满分；配置中的依赖图必须无环。

一份解法描述其覆盖范围、需求能力、构思时间、码量、运行复杂度和内存需求。例如同题可包含暴力 20 分解法、特殊性质 30 分解法、满分 100 分解法。

- 选择满分解法时覆盖的低档子任务由配置明确，不假设所有低档点必然通过。
- 捆绑测试组必须整组通过才计分；组内一个点 WA，整组该子任务为 0。
- 有依赖的子任务必须同时满足前置子任务；独立子任务互不扣分。
- 同一提交中的数组越界可能同时影响多个子任务，不能把每个子任务独立抽签当作互不相关的结果。
- 期望得分可用 Σ(子任务分值 × 通过概率)分析平衡；正式结果必须生成同一份提交所对应的一组通过与失败结果。

### 4.1 算分示例

| 子任务 | 分值 | 依赖 | 提交版本结果 |
|---|---:|---|---|
| 小数据 | 20 | 无 | 通过 |
| 特殊性质 | 30 | 无 | 通过 |
| 完整数据 | 50 | 小数据、特殊性质 | 因整数溢出失败 |

此提交得分为 **50 / 100**。四题结果 100、50、30、0 时，总分为 **180 / 400**。如果修复溢出后截止前成功提交，则按赛事配置重新选择最终版本。

### 4.2 多次提交

规则包必须在“最后一次有效提交”和“单题最高有效得分”中显式选择。前者可能因最后一次改坏而丢分；后者也不能把多个提交各自最好的子任务拼成一份并不存在的 100 分答案，除非规则明确采用逐子任务最高分。

MVP 只实现传统题、独立子任务和每题一个最终提交；依赖子任务、交互题、提交答案、ACM 罚时为后续扩展。

## 5. 赛中信息与封榜

| 模式 | 学生与玩家可见 | 截止前不可见 |
|---|---|---|
| 无反馈 OI | 编译、自测样例、投入时间、主观把握、允许的公告 | 正式测试点结果、真实总分、真实排名 |
| 有反馈、榜单开放 | 当前规则允许的评测结果、公开榜单 | 隐藏测试点细节、他人代码 |
| 有反馈、榜单封榜 | 自己按规则仍可见的评测反馈、封榜前榜单 | 封榜期间他人新增成绩 |
| 赛后复盘 | 正式分数、子任务、错因和允许公开的回放 | 未获授权的他校私人数据 |

无反馈 OI 赛的“屏幕状态”可以写“样例通过”“正在对拍”“自认为完成”，不能提前播放真实 AC 动画。开发调试界面可以查看真实状态，但不得混进玩家界面。

## 6. 评测环境与设备

- 选手电脑影响编辑、编译、稳定性；正式得分中的运行时间取决于题目解法、正式评测环境和编译选项。
- 校内高配电脑不能直接使正式赛答案运行更快。训练评测机过快造成的错误预期，体现为学生选择不可靠的卡常解法。
- 时间复杂度与常数、内存估计共同生成 AC / TLE / MLE；文件名错误可导致整题无法读入。
- CE、RE 等错误按实际原因决定影响范围。重评不重新生成解法、学生错误或运气。
- 停电、换机和补时按统一赛事规则处理；本校学生与外校学生使用相同规则。

## 7. 对手、排名、划线与名额

比赛开始前锁定对手名单、属性与参赛条件。AI 对手使用同一评分模型，规模较大时允许批量计算，但不在玩家得分后临时生成“刚好多一分”的对手。

1. 先按赛事计分规则形成总分，再按排名范围生成榜单。
2. 奖项线、参赛资格线、晋级名额分别计算，不把“获奖”当作必然“有资格”。
3. 默认奖项同分同奖，可超过目标比例；晋级为固定容量，按预先公布的同分规则处理。
4. 同分规则可包含指定场次成绩、指定题得分和公开加赛；不能用隐藏 RP 或内部学生 ID 决定关键名额。
5. 如规则包允许抽签，使用公开可复现的抽签记录；不得在开奖后改变规则。
6. 承办奖励名额先进入名额池，再走资格校验，不直接更改已经公布的总分。

## 8. 复核、申诉与幂等结算

MVP 可直接发布最终成绩；完整赛季阶段保留临时榜单和复核窗口。奖励、晋级和校史在最终成绩确认后发放。

申诉必须引用证据，如文件校验、评测环境错误、勘误公告或漏计分。真实错误存在时按规则纠正；没有错误时不能靠沟通值掷骰加分。

重评保存提交、配置差异、旧结果、新结果和裁定原因。同一场次、学生、奖励类型形成唯一结算键，重复读取成绩或重放事件不得重复发钱。最终成绩后发现重大问题时，通过差额事务更正并保留记录。

## 9. 赛后报告与验收

报告至少区分：知识缺口、时间不足、实现错误、策略错误、环境不适应、异常事故。推荐下一步动作应指向相应课程、检查习惯或休整安排。

| 场景 | 应有结果 |
|---|---|
| 无反馈比赛中打开所有面板 | 仍看不到真实得分和隐藏榜单 |
| 同一比赛在不同倍速、帧率下运行 | 提交过程、得分和名次一致 |
| 截止时仅剩未提交的满分草稿 | 不计分，报告说明未提交 |
| 重新评测同一提交与同一环境 | 结果完全相同 |
| 先确认奖励，再重新打开成绩 | 奖励只到账一次 |
| 两名学生压同分线 | 按已公布规则处理，不临时补规则 |
