# 模拟架构、数据与存档

[返回 README](../README.md) · [时间规则](02-time-and-training.md) · [开发验收](09-development-plan.md)

本篇是实现建议与验收契约。仓库当前没有下述模块、schema、命令或运行时；目录示意不代表已经建立代码工程。引擎仍待原型验证。

## 1. 架构目标与候选引擎

首要目标是让核心模拟能脱离画面运行，并验证相同输入在不同倍速下得到相同结果。

| 候选 | 适用前提 | 原型要验证的事 |
|---|---|---|
| Godot 4 | 桌面独立游戏，偏好集成编辑器与轻量部署 | 3D 像素表现、数据驱动 UI、批量学生渲染 |
| Unity | 团队已有 C# 经验或现成 3D 管线 | UI 与模拟分离、构建体积、资源迭代成本 |
| Three.js | 浏览器体验与快速分享优先 | 本地存档可靠性、长时间模拟、UI 和渲染性能 |

引擎选择完成前，先定义纯数据输入与输出，不承诺多平台同步发布。像素化风格由低分辨率渲染、材质和后处理组合验证，避免过早投入全套美术。

## 2. 模块边界

~~~mermaid
flowchart LR
    UI[界面与场景] --> CMD[命令校验]
    CMD --> SIM[模拟核心]
    CFG[配置与规则快照] --> SIM
    SIM --> TRAIN[训练与生命周期]
    SIM --> CONTEST[比赛模拟]
    SIM --> WORLD[事件与世界]
    SIM --> LEDGER[财务与名额账本]
    SIM --> OUT[状态快照与领域事件]
    OUT --> UI
    OUT --> SAVE[存档与校史]
~~~

- **时钟与日程**：唯一持有标准日期和推进顺序；其他模块不能各自增加游戏天数。
- **训练与学生**：计算成长、状态和生命周期，不直接修改账本。
- **比赛**：保存参赛快照、解题过程、提交与评测版本，输出成绩结算请求。
- **经济与名额**：校验并应用资金、合同、库存和席位事务，维护唯一账本。
- **事件与政策**：只通过允许的效果请求改变状态，保留生效范围与版本。
- **表现层**：读取快照和已公开领域事件；动画、粒子和镜头随机数不进入模拟流。
- **存档层**：持久化完整状态及配置引用，不承担游戏规则判定。

模块间通过命令与结果交互，避免界面直接改学生属性或删除名额。首次原型可在同一进程实现这些职责，不需要先搭建复杂服务。

## 3. 命令与幂等

一次操作包含 command_id、预期状态版本、执行边界、类型与参数。提交后重新校验资格、目标存在性和资源；失败返回原因与可恢复操作。

同一 command_id 只应用一次。已完成的活动使用 activity_instance_id，比赛奖励使用赛事届次、学生和奖励类型形成唯一键，事件选项使用事件实例和选项 ID。

每个边界采用“读取快照 → 校验 → 计算差异 → 整体提交”。资源不足或配置错误时不提交一半差异。时段处理中不允许 UI 修改参与者或赛题。

只为当前需求保留近期命令去重记录和永久关键交易 ID；不要求一开始建立全量事件溯源系统。

## 4. 数据与标识

建议分成静态配置和运行状态。配置保存规则；存档保存实体、已执行结果、计数器与引用的配置版本。

| 对象 | 关键字段 | 不变量 |
|---|---|---|
| Student | id、grade、lifecycle、attrs、knowledge、goals | 属性有界、年级不回退、档案 ID 不复用 |
| Activity | id、slots、participants、leader、room | 同一时段资源不重复占用 |
| Knowledge | id、prerequisites、xp_thresholds | 前置图无环、阈值严格递增 |
| Problem | id、version、solutions、subtasks | 分值和等于满分、依赖无环 |
| Contest | edition_id、rule_snapshot、submissions、result_version | 参赛与规则快照开赛后锁定 |
| HostingProject | id、state、tasks、budget、grant_tranches | 状态转换合法、补贴总和不重复 |
| QuotaBatch | id、source、validity、eligibility、counts | 可用、预留、已用、到期等数量之和守恒 |
| EventInstance | id、template_version、target、node、status | 一个节点只结算一次 |
| LedgerEntry | transaction_id、amount、category、source | 金额为整数、事务唯一 |

### 4.1 学生状态示例

{
  "id": "stu_000001",
  "name": "林澈",
  "grade": 7,
  "generation": 1,
  "lifecycle": "active",
  "attrs": {
    "think": 62,
    "code": 55,
    "detail": 48,
    "mental": 70,
    "learn": 66,
    "energy": 80,
    "mood": 70,

  },
  "skills": { "strategy": 45, "debug": 40, "partial_score": 50, "constant_opt": 30 },
  "condition": { "fatigue": 20, "stress": 35, "burnout": 10 },
  "knowledge": {
    "binary_search": { "total_xp": 570, "peak_level": 3, "last_practiced_day": 12 }

total_xp 是累计经验；本例对应 Lv.3，级内 120 / 250。fatigue 和 energy 分开保存。档案中的 revealed_talents 控制玩家可见信息，不能在 UI 读取全部 talents 后自行决定隐藏。

### 4.2 名额批次示例

~~~json
{
  "id": "quota_host_camp_y1",
  "source": "hosting_camp_y1",
  "rule_version": 1,
  "type": "camp_seat",
  "season": 1,
  "valid_until": { "year": 1, "month_index": 10, "day_index": 10, "slot": 0 },
  "eligibility": { "min_grade": 7, "max_grade": 11 },
  "transferable": false,
  "carry_over": false,
  "total": 2,
  "available": 1,
  "reserved": ["stu_000001"],
  "used": [],
  "expired": 0,
  "revoked": 0
}
~~~

数量守恒为 total = available + reserved.length + used.length + expired + revoked。转让时形成来源批次扣减和新批次增加的同一事务，不复制原始名额。

~~~text

  simulation/        # 时钟、命令、结算调度
  students/          # 成长与生命周期
  contests/          # 解题、提交、评测

  world/             # 事件、政策、竞争学校

  knowledge/
  problems/
  events/
  policies/
  hosting/

~~~

初期配置只采用 JSON，策划表格以后再导出成同一 schema。新增文件并不等于引擎自动发现；加载清单、唯一 ID 和依赖校验需要实现。

## 5. 随机性与可复现

世界种子只在创建新档时生成。使用明确定义版本的伪随机算法，拆分招生、赛事、事件、设备和 AI 学校的随机流，并保存每个流的状态或计数器。

对局部结果可使用稳定键：世界种子 + 赛事届次 + 学生 ID + 题目 ID + 解法或提交版本。不要使用每次启动会变化的语言内置 hash。迭代集合时按稳定 ID 排序，避免容器遍历顺序改变随机抽样顺序。

- 打开面板、播放动画、截图和切换倍速不消耗模拟随机数。
- 保存只读状态，不额外推进随机流；读档恢复未完成赛事的同一进度。
- 配置版本参与结果上下文，同一旧存档应使用相同规则快照或明确迁移。
- 普通跨平台同值应使用固定运算顺序和精度；若未来要跨引擎逐位一致，需另行确定定点数或统一数学实现，当前不作保证。

用规范化的状态摘要比对模拟结果，排除 UI 展开状态、渲染时间和保存时间戳。需要诊断时输出最近一段命令、种子、配置版本和领域事件，默认不包含用户本机绝对路径。

## 6. 存档契约与迁移

存档至少包含 schema_version、game_version、content_version、世界种子、各随机流状态、标准日期、学校、学生、设备、计划、活动进度、事件队列、政策、对手、名额、账本和校史。

- 自动存档放在完整逻辑事务之后；每天日末保存，并在重大结算后保留检查点。
- 默认轮换保留最近 3 份自动档，手动档独立。跨年另有年度快照，不覆盖所有恢复点。
- 写临时文件后校验序列化、版本和完整性，再使用目标平台支持的原子替换；保留上一份有效档。替换失败时保留旧档与临时档，不先删除旧档。
- checksum 检查文件意外损坏，不作为防作弊或安全认证。
- 加载顺序为读取、完整性检查、版本检查、逐步迁移、引用验证、生成运行状态；全部成功后才替换当前游戏。
- 遇到更高且不支持的 schema_version 时拒绝加载并说明版本，不尝试猜测字段含义。
- 配置丢失时指出具体规则包与对象 ID；不把缺失赛题静默替换成新题，不丢弃已有学生和历史。

迁移函数按 v1 → v2 → v3 顺序执行，并保留迁移前备份。日期、XP 累计语义、名额统计和已结算奖励都属于需要明确迁移的字段。

## 7. 配置校验与 Mod 边界

加载时校验类型、数值范围、引用、唯一性、知识图与子任务依赖图、概率、分值总和和事件选项回退。

Mod 为后续功能。初版只加载受控数据，不支持任意本机脚本。规则扩展需要命名空间、版本、依赖列表和存档引用；移除 Mod 后不能自动声称旧档仍兼容。

## 8. 验证与性能

核心规则用少量有明确预期的场景验证：一周训练、无反馈赛、跨月账单、跨年退役、名额失效、事件重复确认、损坏存档恢复。对不变量可增加多种子批量模拟，关注负现金、重复奖励、资源重叠和属性越界。

性能只给验收场景，不提前承诺硬件无关帧率：50 名本校学生、配置化的地区对手、连续推进一年，观察模拟耗时、事件队列和存档增长。渲染帧率与纯模拟耗时分别报告；确定目标平台与基准机器后再定具体阈值。

多年校史按年聚合，保留关键成绩和更正记录；不永久保存每一帧表现数据。年度快照的体积和保留策略需在长线阶段测量。

## 9. 扩展系统的持久化契约

这些字段随对应阶段接入，不能因为界面暂时没有显示就省略保存。它们主要保证同一计划、事件和历史在存读档后继续保持语义。

| 状态族 | 必须保留的事实 | 读取与去重约束 |
|---|---|---|
| 世界身份 | world_id、root_world_id、固定场景ID/版本、分支来源 | 复制不生成新根身份，分支不冒充独立开局 |
| 课程与题库 | 课程版本、题目族、接触与独立完成记录、题目保密状态 | 改名不重置熟题，缺失内容进入待修复而非随机替换 |
| 工作团队 | 合同版本、起止日期、剩余容量、排班、薪资和交接 | 读档不返还已用工时、不重复发薪 |
| 关系与承诺 | cause_key、对象、事实来源、承诺键、截止、兑现状态 | 故事与事件使用同一实例，不重复创建主要诉求 |
| 施工与后勤 | 项目状态、阶段付款、到货、临时场地、维修与库存 | 在途设备和施工区不计可用容量 |
| 合作项目 | 交付阶段、备课授课、应收已收、限定用途与退款 | 实物不算现金，同笔款项只入一次账 |
| 计划与委派 | 模板版本、已展开实例、锁定、预算周期与已用量 | 保存后不重新展开同一周或恢复额度 |
| 策略状态 | 休整状态、进入日期、被替换原活动、待恢复安排、当日重排数 | 疲劳位于进入/退出阈值之间时仍恢复正确状态 |
| 成长证据 | 学生/标准时段、能力份额、证据ID、周起点、已结算标记 | 每人每段最多1点，跨年余量与退役结算不重领 |
| 天赋观察 | 真实ID、已知ID、线索、环境适应与有界触发记录 | 揭示不新增槽位、读档不重新抽灵感 |
| 视觉表达 | 装饰布局、素材引用、匿名、玩家文字与摆拍标记 | 表现不改得分和出勤，自写回忆不作成就事实 |
| 成就证据 | 条件版本、完成时间、归档事实引用、模式 | 不从空样本得出全员达成，不提前泄露赛果 |

### 9.1 本机成就档案与世界存档

绝大部分成就跟随世界保存；“两个特色剧本各完成一年”使用[本机成就档案](18-achievements-and-player-expression.md#21-跨剧本的本机成就档案)。世界年度归档先提交事实证据，再向本机档案登记。登记失败时保留世界中的待同步证据，后续重试按唯一键合并，不回滚已完成学年，也不重复发放任何游戏内资源。

两套文件各自校验、备份和迁移。普通复制与年度分支保留root_world_id，两个不同场景必须来自独立根世界才构成跨剧本经历。这里不提供防篡改认证承诺，也不要求账号与云端服务。

### 9.2 事实、估计、计划与表现分层

真实能力、学生已知信息、教练观察估计和未来计划使用不同字段。比赛后台真实评测、玩家可见反馈和回放公开权限也分开。这样可以让无反馈赛的场景、声音、成就与导出统一使用可见快照，避免每个面板自行隐藏字段时漏出结果。

计划引用真实对象与配置，但尚未执行的预约不等于事实；承诺、扩建草图和合同报价不能直接计入成长、有效机位或收入。每个系统应清楚输出“计划已建立”“资源已锁定”“活动已完成”中的哪一种结果。

### 9.3 配置关系与扩展采用

课程节点依赖、设施套件、岗位要求、场景初值、难度修正、赛事包和事件库应形成可检查的引用清单。加载一个扩展前检查其前置系统已接入；例如没有合同模块的MVP不能显示可用工资套餐，没有题目族记录就不能开放自动换题。

文档中的示例数值不自动组成一个配置包。制作时应为被采用的套餐分配稳定版本，校验哪些费用已包含、哪些需要另计，并保留默认规则的来源。
